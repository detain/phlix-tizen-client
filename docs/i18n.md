# i18n — client → `@phlix/ui` message wiring

Status: **pipeline wired + proven; English-only catalogs.** This document describes
the path a translated string takes from this repo into the rendered UI, and the
exact steps to ship a second language.

## The seam (lives in `@phlix/ui`, resolved pin `v0.99.4`)

`@phlix/ui` ships a config-time i18n seam (its "R6.5c"):

- `PhlixAppConfig.messages?: PhlixMessagesConfig` — a deep-partial `group.key`
  override map over the ui `DEFAULT_MESSAGES` catalog
  (`node_modules/@phlix/ui/dist/app/types.d.ts:111-115`).
- `createPhlixApp()` spreads the consumer config and `provide()`s it under the
  `'phlixConfig'` key; components resolve strings through
  `useMessages().t('group.key')`, which injects that config and builds
  `createTranslator(config?.messages)`
  (`node_modules/@phlix/ui/dist/composables/useMessages.d.ts`).
- Merge semantics (`mergeMessages`, exported): for **each group that exists in
  the English defaults**, `{ ...defaults[group], ...overrides[group] }`.
  Consequences for locale files:
  - partial groups are fine — omitted keys fall back to ui's English;
  - an unknown **top-level group** is dropped (merge iterates only default groups);
  - unknown keys inside a known group ride along in the merged object but no
    adopted ui call site renders them — override only real `group.key` pairs.
- Omitting `messages` renders ui's English byte-for-byte. That was this client's
  state before this wiring; it is why the change is behavior-preserving.

## The client side (`src/i18n/`)

```
src/i18n/index.ts        — resolveLocale() + messagesForLocale() + catalog registry
src/i18n/locales/en.ts   — English override table: intentionally EMPTY
```

`boot()` (src/main.ts) now passes:

```ts
messages: messagesForLocale(resolveLocale())
```

### Locale priority (`resolveLocale`)

1. **explicit** — a caller-supplied app-config value (argument; future Settings
   integration threads through here).
2. **`VITE_PHLIX_LOCALE`** — build-time env constant (declared in `vite-env.d.ts`).
3. **`navigator.language`** — the unprivileged webview signal. Tizen doctrine
   forbids `tizen.systeminfo` device-locale reads without an extra privilege
   (same precedent as `src/discovery/lanDiscovery.ts` / the S503 manifest mask);
   `navigator.language` requires none.
4. **`'en'`** — `FALLBACK_LOCALE`.

Candidates are normalized to the lowercase primary BCP-47 subtag
(`'en-US'`/`'en_US'`/`'ES'` → `en`/`es`) and must hit the registry to win — an
unsupported higher-priority signal falls through to the next, never past the
fallback. `messagesForLocale` parses its input the same way (a mistyped locale
selects the fallback catalog instead of throwing at boot).

### Why `en` ships an empty override

`@phlix/ui` already IS the English catalog. Duplicating ~407 strings client-side
would only create drift. The correct `en` entry is `{}`: ui's `mergeMessages`
reproduces the defaults exactly. (A TV-specific English rewording, if ever
needed, lands in `src/i18n/locales/en.ts` — not by forking ui.)

## Adding a locale (e.g. Spanish) — three edits

1. New file `src/i18n/locales/es.ts`:

   ```ts
   import type { PhlixMessagesConfig } from '@phlix/ui';
   export const ES_MESSAGES: PhlixMessagesConfig = {
     common: { retry: 'Reintentar', close: 'Cerrar' }, // partial groups OK
   };
   ```

2. `src/i18n/index.ts` — extend the union + data list:
   `export type SupportedLocale = 'en' | 'es';` and
   `SUPPORTED_LOCALES: readonly SupportedLocale[] = ['en', 'es'];`
3. `src/i18n/index.ts` — one registry line:
   `es: () => ES_MESSAGES,`

Keys are type-checked against ui's catalog (`PhlixMessagesConfig`), so a typo'd
`group.key` fails `npm run typecheck` rather than silently rendering English.

## Proof (what the tests pin)

`tests/unit/i18n.test.ts` runs the REAL `@phlix/ui` bundle (no mocks):

- a fake override `{ common: { retry: 'ZZZ-TEST' } }` passed to the real
  `createPhlixApp()` renders `ZZZ-TEST` through the real
  provide → inject → merge → `useMessages().t` chain, while an untouched sibling
  key in the same group still renders `'Close'`;
- omitting `messages`, and passing the shipped empty `en` catalog, both render
  the untouched English defaults (behavior-preservation pins);
- `mergeMessages` group semantics (unknown group dropped, `null` group degrades
  to English, fresh object per call);
- the full `resolveLocale` priority table incl. env-stubbed and
  cross-product "never returns unsupported" sweeps.

`tests/unit/main.test.ts` pins that `boot()` actually passes the `messages`
field (present, `=== {}` for en) into `createPhlixApp`.

The seam is proven to the render call; the last stretch — walking the full
router-mounted shell — is intentionally not exercised headlessly (its navigation
guards init auth over the network); the probe components above consume the exact
provide-context object the factory produced, which is what every ui component
 injects.

## Tizen-own catalog (`src/i18n/tizen/`) — strings outside the seam

The ui seam above only reaches strings `@phlix/ui` RENDERS. Everything the
Tizen client renders itself — boot chrome, the nine root-mounted overlays, the
D-pad pages, the Quick-Connect panel — lives OUTSIDE it and flows through a
second, client-local catalog with identical semantics.

### Why a second catalog

The overlays/pages mount as SEPARATE Vue root apps
(`ChapterOverlay → #phlix-chapter-overlay`, `QuickConnectPanel →
#phlix-quick-connect`, … — see `main.ts` boot()). They share only pinia +
router with the main app, so ui's provide/inject `useMessages()` cannot reach
them. They resolve text through the plain function `tTizen()` instead — same
two-level `group.key` shape, same `{param}` tokens, same merge law as ui's
`DEFAULT_MESSAGES`, so the two catalogs read alike.

### Files

- `src/i18n/tizen/locales/en.ts` — `TIZEN_EN`: the complete English base
  (197 keys / 18 groups). Every value is the EXACT literal that previously sat
  inline at its call site; `tests/unit/tizenI18n.test.ts` pins each one
  verbatim (the byte-identity contract — changing a rendered English string
  requires changing the test).
- `src/i18n/tizen/index.ts` — the accessor: `tTizen(key, params?)`,
  `createTizenTranslator` (pure), `mergeTizenMessages`,
  `setTizenLocale`/`tizenLocale`/`clearTizenLocale`, and the
  `TIZEN_CATALOG_OVERRIDES` registry. Unknown keys echo the raw key AND warn
  loudly in dev (`import.meta.env.DEV` →
  `console.warn('[phlix:i18n:tizen] unknown message key:', key)`). Plural
  pipe-forms (`'one|other'`) are selected by `params.count` through ui's own
  exported `selectPluralTemplate` — no forked plural math.

### One locale truth

`src/i18n/tizen/index.ts` REUSES `resolveLocale()` / `SupportedLocale` /
`isSupportedLocale` from `src/i18n/index.ts` — there is no second locale
resolver. `boot()` resolves the locale ONCE and threads the same value into
both catalogs:

```ts
const locale = resolveLocale();
setTizenLocale(locale);           // tizen-own catalog
// … createPhlixApp({ messages: messagesForLocale(locale), … })  // ui seam
```

So the two catalogs can never disagree about which locale is active.

### Adding a locale — BOTH catalogs in lockstep

For a new locale `xx`, five edits total (three for the ui seam, two for the
own catalog):

1. **ui seam** — `src/i18n/locales/xx.ts` exporting `XX_MESSAGES satisfies
   PhlixMessagesConfig` (partial groups OK; see "Adding a locale" above).
2. **ui seam** — add `'xx'` to the `SupportedLocale` union +
   `SUPPORTED_LOCALES`, and one line `xx: () => XX_MESSAGES` in
   `MESSAGE_CATALOGS` (`src/i18n/index.ts`).
3. **tizen-own** — `src/i18n/tizen/locales/xx.ts` exporting
   `XX_TIZEN_MESSAGES satisfies TizenMessagesConfig` (deep-partial over
   `TIZEN_EN`; a full translation file may instead declare
   `satisfies TizenCatalog` so TypeScript forces key-set parity with English).
4. **tizen-own** — one registry line `xx: () => XX_TIZEN_MESSAGES` in
   `TIZEN_CATALOG_OVERRIDES` (`src/i18n/tizen/index.ts`). The union from step
   2 makes a missing entry here a COMPILE error — the registry cannot drift.
5. Nothing else: `boot()` already feeds both catalogs from the same
   `resolveLocale()` result.

Partial overrides fall back to English PER KEY
(`mergeTizenMessages`: `{ ...enGroup, ...xxGroup }`; unknown groups are
dropped, mirroring ui's `mergeMessages` law).

### Module-evaluation-time strings

Tizen locale resolution is SYNCHRONOUS (build-time `VITE_PHLIX_LOCALE` +
`navigator.language` — no startup state), so module-scope catalog tables are
safe. Two deliberate patterns:

- `buildMenu()` runs at boot AFTER `setTizenLocale()`, never at import time.
- `AUDIO_TRACK_APPLY_UNSUPPORTED_UI_STORE` (AudioTracksPage.vue) intentionally
  stays a literal English module-scope EXPORT ANCHOR — the boundary tests
  import it; the RENDERED refusal flows through
  `tTizen('audioTracks.applyRefusal')` and a test pins the two byte-equal.

### What is deliberately NOT in the catalog

- **Wire identity**: `deviceName: 'Phlix for Samsung TV'` in
  `buildPhlixHeaders` (main.ts) and the pairing `identity` field
  (QuickConnectPanel) go to the SERVER — excluded. (The eyebrow that DISPLAYS
  the same words IS cataloged: `quickConnect.eyebrow`.)
- **`KeyMapping.DISPLAY_NAMES`** (remote/KeyMapping.ts): dual-use — they are
  both ActionToast captions AND the phrases registered with
  `tizen.voicecontrol` (`voiceControl.ts`). Translating them would change what
  is registered with the platform voice API; excluded pending a dedicated
  design.
- **`useSyncPlayStore.ts`** error/ws strings: no Tizen template renders them;
  excluded.
- **Punctuation / typography / format notation** that carries no words:
  `'—'`, `'·'`, `'–'`, `'×'`, `'▶'`, `'%'`, `'/ 10'`, `', '`, `'•••'`,
  channel formats `'5.1'`/`'7.1'`/`'7.1.4'`.
- **Brand**: the `'Phlix'` wordmark (incl. `index.html <title>`).
- **CSS-only splash**: `boot.splashHint` (`'Booting'`) IS cataloged and
  test-pinned against `index.html`, but deliberately NOT JS-wired — the S515
  AD-3 splash renders from the first HTML frame with zero JS in its
  lifecycle; translating it is a future build-time (package-step) concern.
- Wire VALUES like the `'ad'` marker-type tag (ChapterOverlay) and CSS font
  names (`'Fraunces'`).
- `src/tizenBridge.ts` contains NO user-facing literals (verified — only
  selectors and boolean state).
