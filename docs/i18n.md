# i18n — client → `@phlix/ui` message wiring

Status: **pipeline wired + proven; SIX locales shipped (2026-09 estate decision).**
This document describes the path a translated string takes into the rendered UI,
the vendored ui-SSOT bundles, and the exact steps to ship another language.

## Locale matrix (what ships today)

| Tag | ui seam (vendored from phlix-ui SSOT) | tizen-own catalog | Notes |
|-----|--------------------------------------|-------------------|-------|
| `en` | `{}` empty override (ui IS the English catalog) | `TIZEN_EN` base (197 keys) | byte-identity pins in both suites |
| `es` | `ui-locale-bundles/es.ts` | `tizen/locales/es.ts` | neutral Latin-American, tú |
| `fr` | `ui-locale-bundles/fr.ts` | `tizen/locales/fr.ts` | vous register |
| `de` | `ui-locale-bundles/de.ts` | `tizen/locales/de.ts` | du register |
| `it` | `ui-locale-bundles/it.ts` | `tizen/locales/it.ts` | informal |
| `pt_BR` | `ui-locale-bundles/pt_BR.ts` | `tizen/locales/pt_BR.ts` | Brazilian; EVERY `pt-*` device signal maps here (region-aware normalization) |
| `ja` | `ui-locale-bundles/ja.ts` | `tizen/locales/ja.ts` | zero pipe templates — CLDR "other"-only with native counters (人/枚/曲/件/章/本) |

Both registries are keyed by the same `SupportedLocale = 'en' | PhlixLocaleCode`
type, so a tag can exist in one catalog and not the other only as a COMPILE
error. The full integrity law (key-set identity, placeholder parity, segment
counts, EN-leak allow-lists, hash pins) lives in
`tests/unit/i18nLocales.test.ts`.

## The seam (lives in `@phlix/ui`, resolved pin `v0.99.5`)

`@phlix/ui` ships a config-time i18n seam (its "R6.5c"):

- `PhlixAppConfig.messages?: PhlixMessagesConfig` — a deep-partial `group.key`
  override map over the ui `DEFAULT_MESSAGES` catalog
  (`node_modules/@phlix/ui/dist/app/types.d.ts:111-115`).
- `createPhlixApp()` spreads the consumer config and `provide()`s it under the
  `'phlixConfig'` key; components resolve strings through
  `useMessages().t('group.key')`, which injects that config and builds
  `createTranslator(config?.messages)`
  (`node_modules/@phlix/ui/dist/composables/useMessages.d.ts`).
- Merge semantics (`mergeMessages`, exported): for **each group that exists in
  the English defaults**, `{ ...defaults[group], ...overrides[group] }`.
  Consequences for locale files:
  - partial groups are fine — omitted keys fall back to ui's English;
  - an unknown **top-level group** is dropped (merge iterates only default groups);
  - unknown keys inside a known group ride along in the merged object but no
    adopted ui call site renders them — override only real `group.key` pairs.
- Omitting `messages` renders ui's English byte-for-byte. That was this client's
  state before this wiring; it is why the change is behavior-preserving.

## The client side (`src/i18n/`)

```
src/i18n/index.ts             — resolveLocale() + messagesForLocale() + catalog registry
src/i18n/locales/en.ts        — English override table: intentionally EMPTY
src/i18n/ui-locale-bundles/   — SIX vendored full bundles + PIN (sha-pinned from phlix-ui)
src/i18n/tizen/               — tizen-own catalog: base en.ts (197 keys) + six locale files
```

`boot()` (src/main.ts) now passes:

```ts
messages: messagesForLocale(resolveLocale())
```

### Locale priority (`resolveLocale`)

1. **explicit** — a caller-supplied app-config value (argument; future Settings
   integration threads through here).
2. **`VITE_PHLIX_LOCALE`** — build-time env constant (declared in `vite-env.d.ts`).
3. **`navigator.language`** — the unprivileged webview signal. Tizen doctrine
   forbids `tizen.systeminfo` device-locale reads without an extra privilege
   (same precedent as `src/discovery/lanDiscovery.ts` / the S503 manifest mask);
   `navigator.language` requires none.
4. **`'en'`** — `FALLBACK_LOCALE`.

Candidates are normalized to the lowercase primary BCP-47 subtag
(`'en-US'`/`'en_US'`/`'ES'` → `en`/`es`) — with one region-aware exception:
every Portuguese signal (`pt`, `pt_BR`, `pt-PT`, `pt-419`, …) resolves to the
single shipped `pt_BR` key, because collapsing it to bare `pt` would miss the
registry and silently degrade every Portuguese device to English (showing
Brazilian Portuguese to European viewers beats showing them English; a future
second pt variant is a registry addition, not a resolver rewrite). A parsed
tag must hit the registry to win — an unsupported higher-priority signal falls
through to the next, never past the fallback. `messagesForLocale` parses its
input the same way (a mistyped locale selects the fallback catalog instead of
throwing at boot).

### Why `en` ships an empty override

`@phlix/ui` already IS the English catalog. Duplicating ~412 strings client-side
would only create drift. The correct `en` entry is `{}`: ui's `mergeMessages`
reproduces the defaults exactly. (A TV-specific English rewording, if ever
needed, lands in `src/i18n/locales/en.ts` — not by forking ui.)

## Vendoring the ui bundles (SSOT = phlix-ui)

The six translated ui catalogs are NOT authored here. `@phlix/ui` owns them;
this repo keeps SHA-PINNED copies under `src/i18n/ui-locale-bundles/` plus a
`PIN` manifest (pinned branch/ref + per-file `source_sha256` and
`vendored_sha256`). Copying applies exactly ONE deterministic transform
(documented in `scripts/sync-ui-locale-bundles.mjs` and echoed in
`PIN.transforms`):

1. `import type { PhlixMessages } from '../messages';` →
   `import type { PhlixMessages } from '@phlix/ui';` — there is no such module
   client-side, and since v0.99.5 the type is a declared barrel export.

Everything else is VERBATIM: the bundles keep `satisfies PhlixMessages` and the
registry keeps `Record<PhlixLocaleCode, PhlixMessages>`, so the client build
compile-checks the vendored key sets against the INSTALLED catalog (vue-tsc
proves it; `i18nLocales.test.ts` greps the TEXT so a relaxation can never
silently return).

Strictness history: until the v0.99.5 re-pin the vendor carried TWO extra
relaxation transforms (`satisfies PhlixMessages` → relaxed
`Record<string, Record<string, string>>`). They existed because the dc1df7d5
bundles ran 7 keys (`connect.scan`, `connect.scanning`, `connect.scanFailed`,
`connect.scanEmpty`, `connect.scanListLabel`, `player.seekBackward`,
`player.seekForward`) AHEAD of the installed v0.99.4 pin — `PhlixMessages` is
`typeof DEFAULT_MESSAGES` **of the installed package**, so satisfying it would
have failed on exactly those keys. v0.99.5 ships them: installed and bundles
are EXACTLY equal key-sets (412 keys, both directions asserted in
`tests/unit/i18nLocales.test.ts`), the ahead-of-pin block was replaced by that
equality pin, and the relaxation was deleted with its reason.

Refresh procedure (when ui re-tags or the SSOT bundle changes):

```bash
# 1. sibling checkout must contain the new commit
git -C ../phlix-ui fetch origin
# 2. re-pin: pass the new ref explicitly (a BARE run defaults to the PIN on
#    disk and only re-vendors the current pin — never a rollback; the
#    in-script SOURCE_REF/SOURCE_BRANCH are bootstrap anchors when no PIN
#    exists, and tests/unit/i18nLocales.test.ts hard-fails if they drift
#    from the PIN)
node scripts/sync-ui-locale-bundles.mjs --ref <new-sha-or-tag> --branch <name>
# 3. gates — the source-parity test proves disk == transform(pinned source)
npm run typecheck && npm test && npm run build
# 4. bump the @phlix/ui dependency to the tag containing the new keys FIRST —
#    installed↔bundle equality then holds again; a bundle ahead of the install
#    fails typecheck (satisfies) and flips the equality pin deliberately
git add src/i18n/ui-locale-bundles && git commit…
```

CI drift policy (verified against `.github/workflows/test.yml`): CI clones only
`../phlix-contracts`, never `../phlix-ui`, so the **source-parity test skips in
CI by design** (the skip is named loudly in the suite title) while the PIN↔disk
hash leg runs everywhere. Drift protection therefore rides the local gate
(developers have the sibling; the skip is conspicuous) plus the re-pin cascade
above. A hand-edit of a vendored file without re-running the script breaks the
PIN↔disk hash pin even in CI.

## Adding a locale to the ui seam

1. Author it in phlix-ui (SSOT): `src/i18n/locales/xx.ts` + its registry +
   their suite; land + tag there.
2. Re-vendor here per the procedure above — `LOCALE_MESSAGES` gains the tag,
   `SupportedLocale` follows automatically (it is `'en' | PhlixLocaleCode`
   from the vendored barrel), and the `MESSAGE_CATALOGS` completeness type
   makes the one missing registry line a COMPILE error.
3. Add the tizen-own half (below) and the locale-integrity allow-lists /
   thresholds in `tests/unit/i18nLocales.test.ts` for the new language.

A purely client-local PARTIAL override remains legal (and was the only flow
before the six-locale build-out): hand-written `src/i18n/locales/xx.ts`
(`PhlixMessagesConfig`, partial groups OK) + union/list/registry edits in
`src/i18n/index.ts`. Keys are type-checked, so a typo'd `group.key` fails
`npm run typecheck` rather than silently rendering English.

## Proof (what the tests pin)

`tests/unit/i18n.test.ts` runs the REAL `@phlix/ui` bundle (no mocks):

- a fake override `{ common: { retry: 'ZZZ-TEST' } }` passed to the real
  `createPhlixApp()` renders `ZZZ-TEST` through the real
  provide → inject → merge → `useMessages().t` chain, while an untouched sibling
  key in the same group still renders `'Close'`;
- omitting `messages`, and passing the shipped empty `en` catalog, both render
  the untouched English defaults (behavior-preservation pins);
- `mergeMessages` group semantics (unknown group dropped, `null` group degrades
  to English, fresh object per call);
- the full `resolveLocale` priority table incl. env-stubbed and
  cross-product "never returns unsupported" sweeps.

`tests/unit/main.test.ts` pins that `boot()` actually passes the `messages`
field (present, `=== {}` for en) into `createPhlixApp`.

`tests/unit/i18nLocales.test.ts` is the six-locale integrity gate: key-set
identity across all bundles of both catalogs, verbatim `{placeholder}` parity,
CLDR segment law (tizen-own: latin pipes on exactly the 12 additive-plural
keys, ja zero pipes + native counters), per-locale English-leak allow-lists
pinned in BOTH directions, diacritic/CJK sanity aggregates, the resolution
matrix (device tag → bundle for both catalogs), real-bundle Spanish/Japanese
E2E through `mergeMessages`/`tTizen`, and the vendoring PIN/source drift
guards (CI skip policy documented above).

The seam is proven to the render call; the last stretch — walking the full
router-mounted shell — is intentionally not exercised headlessly (its navigation
guards init auth over the network); the probe components above consume the exact
provide-context object the factory produced, which is what every ui component
 injects.

## Tizen-own catalog (`src/i18n/tizen/`) — strings outside the seam

The ui seam above only reaches strings `@phlix/ui` RENDERS. Everything the
Tizen client renders itself — boot chrome, the nine root-mounted overlays, the
D-pad pages, the Quick-Connect panel — lives OUTSIDE it and flows through a
second, client-local catalog with identical semantics.

### Why a second catalog

The overlays/pages mount as SEPARATE Vue root apps
(`ChapterOverlay → #phlix-chapter-overlay`, `QuickConnectPanel →
#phlix-quick-connect`, … — see `main.ts` boot()). They share only pinia +
router with the main app, so ui's provide/inject `useMessages()` cannot reach
them. They resolve text through the plain function `tTizen()` instead — same
two-level `group.key` shape, same `{param}` tokens, same merge law as ui's
`DEFAULT_MESSAGES`, so the two catalogs read alike.

### Files

- `src/i18n/tizen/locales/en.ts` — `TIZEN_EN`: the complete English base
  (197 keys / 18 groups). Every value is the EXACT literal that previously sat
  inline at its call site; `tests/unit/tizenI18n.test.ts` pins each one
  verbatim (the byte-identity contract — changing a rendered English string
  requires changing the test).
- `src/i18n/tizen/index.ts` — the accessor: `tTizen(key, params?)`,
  `createTizenTranslator` (pure), `mergeTizenMessages`,
  `setTizenLocale`/`tizenLocale`/`clearTizenLocale`, and the
  `TIZEN_CATALOG_OVERRIDES` registry. Unknown keys echo the raw key AND warn
  loudly in dev (`import.meta.env.DEV` →
  `console.warn('[phlix:i18n:tizen] unknown message key:', key)`). Plural
  pipe-forms (`'one|other'`) are selected by `params.count` through ui's own
  exported `selectPluralTemplate` — no forked plural math.

### One locale truth

`src/i18n/tizen/index.ts` REUSES `resolveLocale()` / `SupportedLocale` /
`isSupportedLocale` from `src/i18n/index.ts` — there is no second locale
resolver. `boot()` resolves the locale ONCE and threads the same value into
both catalogs:

```ts
const locale = resolveLocale();
setTizenLocale(locale);           // tizen-own catalog
// … createPhlixApp({ messages: messagesForLocale(locale), … })  // ui seam
```

So the two catalogs can never disagree about which locale is active.

### Adding a locale — BOTH catalogs in lockstep

With the six estate locales shipped, a seventh `xx` means:

1. **ui seam** — author in phlix-ui, then re-vendor (see "Vendoring the ui
   bundles"). The `SupportedLocale` union grows with the vendored
   `PhlixLocaleCode` automatically; the `MESSAGE_CATALOGS` completeness type
   then fails the build until one registry line `xx: () => configOf(LOCALE_MESSAGES.xx)`
   is added in `src/i18n/index.ts` (plus `SUPPORTED_LOCALES`).
2. **tizen-own** — `src/i18n/tizen/locales/xx.ts` exporting
   `XX_TIZEN_MESSAGES satisfies TizenCatalog` — the six shipped files use the
   FULL-catalog form so TypeScript forces key-set parity with English
   (a deliberate partial may still declare `satisfies TizenMessagesConfig`).
3. **tizen-own** — one registry line `xx: () => XX_TIZEN_MESSAGES` in
   `TIZEN_CATALOG_OVERRIDES` (`src/i18n/tizen/index.ts`). The union from step
   1 makes a missing entry here a COMPILE error — the registries cannot drift.
4. **tests** — extend the allow-lists (`EN_LEAK_OK`, diacritic/CJK specs,
   matrix rows) in `tests/unit/i18nLocales.test.ts` for the new language.
5. Nothing else: `boot()` already feeds both catalogs from the same
   `resolveLocale()` result.

Partial overrides fall back to English PER KEY
(`mergeTizenMessages`: `{ ...enGroup, ...xxGroup }`; unknown groups are
dropped, mirroring ui's `mergeMessages` law).

### Module-evaluation-time strings

Tizen locale resolution is SYNCHRONOUS (build-time `VITE_PHLIX_LOCALE` +
`navigator.language` — no startup state), so module-scope catalog tables are
safe. Two deliberate patterns:

- `buildMenu()` runs at boot AFTER `setTizenLocale()`, never at import time.
- `AUDIO_TRACK_APPLY_UNSUPPORTED_UI_STORE` (AudioTracksPage.vue) intentionally
  stays a literal English module-scope EXPORT ANCHOR — the boundary tests
  import it; the RENDERED refusal flows through
  `tTizen('audioTracks.applyRefusal')` and a test pins the two byte-equal.

### What is deliberately NOT in the catalog

- **Wire identity**: `deviceName: 'Phlix for Samsung TV'` in
  `buildPhlixHeaders` (main.ts) and the pairing `identity` field
  (QuickConnectPanel) go to the SERVER — excluded. (The eyebrow that DISPLAYS
  the same words IS cataloged: `quickConnect.eyebrow`.)
- **`KeyMapping.DISPLAY_NAMES`** (remote/KeyMapping.ts): dual-use — they are
  both ActionToast captions AND the phrases registered with
  `tizen.voicecontrol` (`voiceControl.ts`). Translating them would change what
  is registered with the platform voice API; excluded pending a dedicated
  design.
- **`useSyncPlayStore.ts`** error/ws strings: no Tizen template renders them;
  excluded.
- **Punctuation / typography / format notation** that carries no words:
  `'—'`, `'·'`, `'–'`, `'×'`, `'▶'`, `'%'`, `'/ 10'`, `', '`, `'•••'`,
  channel formats `'5.1'`/`'7.1'`/`'7.1.4'`.
- **Brand**: the `'Phlix'` wordmark (incl. `index.html <title>`).
- **CSS-only splash**: `boot.splashHint` (`'Booting'`) IS cataloged and
  test-pinned against `index.html`, but deliberately NOT JS-wired — the S515
  AD-3 splash renders from the first HTML frame with zero JS in its
  lifecycle; translating it is a future build-time (package-step) concern.
- Wire VALUES like the `'ad'` marker-type tag (ChapterOverlay) and CSS font
  names (`'Fraunces'`).
- `src/tizenBridge.ts` contains NO user-facing literals (verified — only
  selectors and boolean state).
